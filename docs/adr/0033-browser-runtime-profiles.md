# Browser Runtime profiles

Status: accepted; App implementation, live source acceptance, and macOS arm64 packaged-App acceptance complete.

Browser Runtime retains `WorkflowBrowserPort.withPage(...)` as its workflow-facing interface and owns launch configuration, browser lifetime, state handling, worker connection, and cleanup as a deep module. The workflow catalog selects a named Browser execution profile rather than exposing engine choices or arbitrary launch flags to provider code. All workflows share a normal Chrome User-Agent derived from the bundled Chromium version by default; a run uses one selected profile and does not silently rotate profiles on failure.

Pre-migration E-Invoice comparisons through the App browser module isolated the default `HeadlessChrome` User-Agent as the cause of a reproducible login-entry rejection: changing only User-Agent yielded 403/200/200/403 in interleaved default/custom/custom/default probes. After applying the normal Chrome User-Agent and moving E-Invoice to the Chromium worker, all eleven browser workflows passed live collection, validation, and Canonical Financial Commit. E-Invoice passed twice, committing 328 of 328 records in both runs; sanitized run identifiers are recorded in the [acceptance table](../specs/app-owned-workflow-runtime.md#live-source-acceptance). ADR 0032's Firefox exception has been removed.

The agreed configuration, development-runtime sharing, and acceptance contract are tracked in the [design record](../specs/browser-runtime-design.md). The user confirmed the design on 2026-09-29. The App implementation and live-source migration have passed. The macOS arm64 packaged-App fixture passed on 2026-09-29 using the actual bundled shell and the normal Electron worker path.

Production packaging includes only Chromium headless shell and required FFmpeg support; developer-headed browsing uses a separately installed full Chromium. Packaging explicitly excludes full Chromium and Firefox left by earlier installations, so payload selection is deterministic rather than dependent on the developer's existing browser directory. The macOS arm64 package contained exactly the manifest-selected shell and FFmpeg payloads and passed actual worker success and cancellation checks. Other OS package artifacts were not built.

Profiles initially vary only observed User-Agent strategies, tested Chromium compatibility switches, and cookie retention or source-domain reset policies. Runtime invariants remain module-owned, and adding configuration requires source evidence. Live acceptance includes one complete App run for every browser source and a second E-Invoice run; all passed on 2026-09-29. The packaged fixture verified actual Browser.version and navigator version against the package manifest, default profile revision 1, page/context closure, runtime-profile cleanup, and sanitized persisted records.

App and developer composition share profile resolution and defaults. Development mode may launch headed Chromium, while production always uses headless shell and supervised workers. Run summaries retain profile ID/revision, Chromium version, and sanitized error codes, without raw launch settings or browser state. The passed packaged-App local fixture verified actual worker/browser execution, profile identity against the live Chromium and navigator versions, cancellation, cleanup, and payload exclusions.
