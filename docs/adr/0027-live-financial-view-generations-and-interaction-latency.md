# Live financial view generations and interaction latency

OctopusBeak product pages present Current Financial Projections through page-scoped Product View Generations. Every generation is fixed to one Canonical Knowledge Point, while its page shell, primary financial view, and secondary analysis may become visible progressively through independent bounded queries. A section failure does not block unrelated sections; a background refresh retains the prior complete generation as explicitly stale until its replacement is ready, and results from an older generation never overwrite a newer one.

Every successful Canonical Financial Commit causes the main process to publish a monotonic operational invalidation signal containing the new knowledge point. The signal carries no financial data or authority. The renderer broadly invalidates all financial route caches, immediately starts a new generation only for the visible route, and leaves hidden routes stale until navigation. Entering a previously visited route shows its last complete generation immediately, performs a cheap freshness check, and refreshes in the background when needed. Automation terminal state performs a final reconciliation but is not the source of financial freshness.

Invalidation is latest-wins. A page has at most one active generation, coalesces a burst of commit signals to the highest observed knowledge point, and does not replay intermediate Current Financial Projections. Work for a superseded generation may be cancelled; if cancellation is unavailable, its result is discarded and cannot replace newer data. The page coordinator first obtains a generation token containing the selected knowledge point, and every component query explicitly supplies that cutoff. Components use independent short-lived reads rather than sharing a page-long database transaction. If the requested cutoff can no longer be served, the whole generation is abandoned and restarted from a newly selected knowledge point.

During a background refresh, the prior generation remains visible until the new primary financial view is complete. The primary view then switches atomically to the new generation. Any secondary financial value that has not completed at that same knowledge point is removed and replaced by a local skeleton; it may appear independently when ready, but a secondary value from the prior generation never remains visible beside the new primary view. This resolves progressive rendering without mixing visible financial knowledge points.

The main process broadcasts every invalidation signal to all live renderer windows. Each window independently tracks its highest observed knowledge point and refreshes only its visible route. Route entry, application resume, window focus, and renderer reconnection perform a debounced latest-knowledge-point check for the visible route to repair missed signals; this is not periodic polling and does not cause hidden routes to query.

Invalidation publication happens only after a successful commit. Failure to deliver the operational signal to a renderer neither rolls back nor changes the reported outcome of the durable financial commit. It produces a sanitized operational warning, and the route-entry, focus, resume, reconnect, or Automation-terminal reconciliation paths repair freshness later. A failed commit emits no invalidation.

The page shell and controls never wait for financial queries. Primary totals and their reconciling account or transaction lists stay within one query component when separating them could display contradictory values; charts, history, allocation, candidate suggestions, and other secondary analysis load independently. First load uses section-local skeleton and error states. If the initial primary query fails, the shell remains usable, the primary section offers a retry, and independently successful secondary sections from the same generation may remain visible. If a background primary refresh fails, the page does not switch and retains the complete prior generation marked `更新失敗`. After the primary view has switched, a failed secondary section shows a local error and retry instead of restoring its prior-generation value. A later invalidation may retry failed work, but the same failure never enters an unbounded immediate retry loop.

Every user operation that establishes a Spending Deduplication Link, including direct pairing and candidate confirmation, has an interaction SLO of p99 at most 200 ms under normal interactive load, measured from confirmation through durable commit and visibility of the updated Current Financial Projection in the affected Spending section. Candidate ranking and recomputation occur before confirmation and are not part of the confirmation critical path. Removing a link uses the same latency budgets. When an Automation commit causes canonical-writer contention, the corresponding p99 is at most 500 ms and the UI acknowledges the in-progress operation within 100 ms while preventing duplicate submission. A loading acknowledgment alone does not satisfy either completion SLO, and unrelated page components are outside the completion boundary.

The pairing command accepts only the purchase and payment transaction identities needed to express the decision. Inside one controlled server command it narrowly revalidates their existence, current eligibility, and absence of an active conflict before writing. It does not trust renderer-supplied reports or eligibility, and it does not rebuild the full Spending projection merely to validate one pair. After commit it returns the smallest recognition result needed to update the affected projection section.

A command initiated from an older Product View Generation is not rejected merely because a newer knowledge point exists. The server validates the referenced purchase and payment against current canonical state. If they remain eligible, the command commits normally; if either was paired, withdrawn, or otherwise became ineligible, it performs no write, returns `spending-pair-stale`, and causes the renderer to load the latest generation and explain that the data changed.

The command response includes its committed knowledge point. After the initiating renderer applies and validates the server-produced patch, that Spending section is current through that point and does not requery for an equal or older broadcast invalidation. Other route caches in that renderer remain stale, and other windows process the broadcast normally. A patch application or validation failure falls back to a complete generation refresh.

Every user pairing command carries a renderer-generated, non-financial idempotency key that remains valid across application restarts. Its uniqueness scope is command kind plus key. Repeating the same key and purchase/payment identities returns the original outcome and an equivalent current patch without appending another decision; reusing a key with different identities fails closed with `idempotency-key-conflict`. If commit visibility is uncertain because the response was lost, the UI displays `讀取中`, performs freshness reconciliation, and does not report failure until the durable outcome is known.

Navigation or generation replacement cancels component work that has not begun and passes a cancellation or generation token to the worker. A short SQLite read that has already begun may finish, but its result is discarded and its resources are released immediately. Cancellation never interrupts a canonical write transaction after it has begun. The 200 ms and 500 ms thresholds are service-level objectives, not transaction deadlines: exceeding them records a latency violation, retains `讀取中`, and prevents duplicate submission while the command reaches commit or rollback. Only a queued command whose write has not begun may be cancelled.

Progressive loading has explicit budgets: the page shell is usable within p95 100 ms of route transition; the primary financial view is visible within p95 500 ms and p99 one second; and each secondary analysis component completes within p95 1.5 seconds without blocking the primary view. Acceptance measurements use at least the observed high-water production ledger scale and record transaction, invoice, and candidate counts together with the test hardware. Tiny synthetic fixtures and fake worker timings are correctness aids, not SLO evidence. The benchmark must separately measure renderer-to-worker request time, durable transaction time, worker response, and the paint that makes the changed projection visible.

Formal latency evidence uses a deterministic synthetic ledger generated from de-identified high-water production statistics and a second dataset at twice that scale. Each scenario contains at least 1,000 timed operations and reports p50, p95, p99, and maximum latency for warm and cold store paths, both with and without canonical-writer contention. Reports record data cardinalities, hardware, and build mode. Shared CI enforces a regression budget; formal p99 acceptance runs in a fixed performance environment.

Performance telemetry is non-financial and privacy bounded. It may record operation kind, span name, duration, knowledge-point distance, cardinality bucket, contention and cold-start flags, success or stable error code, and build or hardware profile. It never records accounts, merchants, invoices, transaction identities, amounts, SQL, filesystem paths, or payloads. Normal application use retains only bounded local rolling aggregates; per-operation traces require an explicitly enabled diagnostic mode.

This decision preserves the atomic Canonical Financial Commit and the all-or-nothing semantics of each individual Canonical Query Boundary request. Progressive rendering creates smaller independent requests at a shared cutoff; it never exposes partial financial effects from an incomplete Capture, Import Run, projection rebuild, or failed query.

## Acceptance

- Every successful Canonical Financial Commit emits one post-commit monotonic invalidation, and a failed commit emits none.
- After Automation writes, the visible financial route refreshes without restarting the application. Hidden routes become stale and perform a freshness check on entry.
- All renderer windows receive invalidation, while focus, resume, reconnect, route entry, and Automation-terminal reconciliation repair missed delivery.
- Commit bursts converge on the highest knowledge point. Superseded, cancelled, navigated-away, and late query or patch results never replace a newer generation.
- Every visible financial value belongs to one knowledge point. The primary view switches atomically, and incomplete secondary sections do not retain values from an older generation.
- Page shell, primary financial view, and secondary analysis have independent loading, ready, and error states; a complete route DTO no longer gates the page shell or unrelated sections.
- Direct pairing, candidate confirmation, and link removal use narrow server-side validation, durable idempotency, and the smallest valid result patch. Their confirmation path does not rebuild the complete Spending report.
- Contract tests cover response loss, duplicate retry, idempotency-key conflict, stale candidates, writer contention, cancellation, local component failure, and commit-event delivery failure.
- Fixed-environment benchmarks execute at least 1,000 warm and cold operations under normal load and writer contention, meet the recorded SLOs, and have a corresponding CI regression budget.
- Telemetry and diagnostics contain no financial or personally identifying data prohibited by this decision.
- Existing migration, repair, projection, Relation Resolution, provider fixtures, and Canonical Financial Commit atomicity retain their behavior.
- Electron acceptance demonstrates that Automation commits become visible in Overview, Assets, Liabilities, and Spending without restart, and that pairing changes appear in the affected section within the applicable SLO.
