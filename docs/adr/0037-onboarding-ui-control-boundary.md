# Centralize onboarding control behind explicit application interfaces

Status: Current

Previously, onboarding control crossed the page controller, Automation dashboard, coach, and global DOM selectors; collection completion changed the coach's target to Overview, while activating that target depended on a simulated click. The implementation centralizes progression, permitted operations, navigation, and highlight selection in an onboarding controller with explicit page operations and registered presentation targets. The overlay renders guidance and blocks interaction outside the highlighted region without inferring or driving application actions through DOM clicks. This adds an integration boundary to maintain so future flow changes remain independent of page markup and presentation state cannot substitute for workflow or data-readiness facts.

Only the fully completed run tracked by the active progression may trigger a fresh Overview read and automatic navigation; partial, failed, cancelled, or replaced runs cannot complete onboarding, even when they committed some data. Non-empty accounts are ready even when coverage is partial. Zero accounts are ready only when the Overview explicitly reports `empty`, or when the tracked successful workflow has typed `no-data` evidence (summary status `no-data`, or a non-empty product list whose dispositions are all `no_data` or `not_held`). Unproven `awaiting` and `unavailable` results remain retryable preparation errors; unrelated source gaps never stand in for proof that the tracked workflow returned no data. The accepted readiness classification is persisted with onboarding so a later run cannot replace its evidence. This does not change financial admission or create a second workflow progress authority.

Onboarding-specific Assist navigation, spotlighting, waiting controls, and verification interaction dependencies have been removed. [ADR 0039](0039-solver-only-verification.md) later removed Assist and manual verification from the product. Onboarding therefore never waits for a person to verify. A verification stage either completes through its solver route or ends the tracked run with a failure.

The controller distinguishes exiting guidance from cancelling execution: exit restores normal navigation and leaves the current workflow running, while onboarding can be entered again only through a fresh restart. Restart preserves entered sign-in details, source selections, and imported data without requiring re-entry; it cancels the previous progression's still-running run, waits until that exact run is terminal, and only then permits a new run. Old run outcomes cannot settle the new progression. This keeps onboarding lifecycle separate from workflow lifecycle while making their explicit coordination the controller's responsibility.

The visible path is persisted as a story ID and node ID. A typed [story definition](../../src/lib/onboarding/story.ts) is the single source for each node's stable ordinal, copy key, target, route, offered commands, and safe Previous transition. Runtime events such as opening the source picker, choosing an institution, saving credentials, starting a run, and accepting Overview readiness move that node through the [onboarding controller](../../src/lib/onboarding/controller.ts); dashboard presentation reports explicit user actions and registers targets, but does not infer progression from modal state or target-specific action labels. Previous is disabled while a workflow or Overview preparation is active. Returning from Overview to review a completed run keeps its readiness evidence and requires an explicit return action, so it cannot replay or automatically loop.

The boundary is implemented in the [onboarding controller](../../src/lib/onboarding/controller.ts), [application adapter](../../src/lib/onboarding/application-port.ts), and [registered target interface](../../src/lib/onboarding/target-observer.ts); page-level integration lives in [the app shell](../../src/routes/+page.svelte).
