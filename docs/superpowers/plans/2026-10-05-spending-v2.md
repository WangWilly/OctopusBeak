# Spending v2 plan

Status: Proposed

Implements the Pencil design "zh-TW · Spending v2（帳目合併改為 Modal）": page A, the 帳目合併 modal B, and the 消費明細 modals C (pending) and D (merged). The model change is [ADR 0038](../../adr/0038-invoice-item-categories-and-purchase-category.md).

## Product decisions (2026-10-05)

- Build the category data side. Invoice-only purchases are categorized per invoice item.
- The first automatic categorization reads e-invoice items and seller identity. Bank-only purchases keep whatever categorization they already have (the Cathay domestic-deposit route already exists) and are otherwise Unclassified until the user changes them.
- Show the month-end projection (月底推估) with its basis (依目前 N 天的步調).
- The merge modal has no 可能重複 and no 退款 tab. It has 待合併 and 已合併, plus 合併紀錄.
- Roll out in phases. The user signs off after each phase.

## Reversible decisions

1. Display groups, in one exhaustive typed mapping shared by the renderer and the query layer. Queries filter by code list.
   - 餐飲: dining, alcohol_and_tobacco
   - 日常: food_and_groceries, personal_and_family_care, healthcare
   - 交通: transportation
   - 購物: clothing_and_footwear
   - 居家: housing_and_utilities, household_goods_and_services, information_and_communication
   - 休閒: recreation_sports_and_culture, travel
   - 其他: insurance, taxes_and_government, gifts_and_donations, work_and_business, education
   - 未分類 is the query-time Unclassified bucket, not a group.
2. 高度相符 (strong match) is a pure read-time function, never stored. A pending invoice/payment pair is strong when the amount and currency are exact (already required), both sides have a purchase-date basis and lie at most one calendar day apart, the pair is the only pending candidate for its invoice and for its payment across all months (excluding records already linked and pairs already confirmed or denied), and seller and bank-description similarity passes a threshold chosen by a real-data measurement in Phase 3. Card payments that only have a posting-date fallback are never strong; that is intended. Every other pending pair is 可能相符. Reason chips are 金額相同 (always), 同一天 or 相差 N 天, and 商家相符 when similarity passes. 帳單號碼相符 is dropped because no data supports it. The similarity function moves from the renderer into the ledger layer.
3. Bulk merge (合併所有高度相符（N 組）) recomputes the strong set at command time inside one commit and writes one user decision event per pair with the evidence that was shown. A conflict is a pair that is no longer pending or no longer strong. Any conflict rejects the batch without writing, and the modal re-offers the recomputed set. A background sync that leaves the offered pairs unchanged does not reject the batch.
4. 稍後處理 only closes the modal.
5. The top-bar 帳目合併 N counts pending pairs across all months. The month panel's 待合併帳目 N 組 stays month-scoped.

## Phases

1. Model and decisions: ADR 0038, CONTEXT.md, the specification pointer and acceptance checks, and this plan.
2. Category data: generalize the Assertion spine with an `einvoice_item` subject (assertions, transitions, provenance, routes, projection, a typed item categorization value table); the first Derived producer; the user change-category command; fix projection sync so generation categorization rows are deleted and reselected with their transactions; the Purchase category on record pages; per-month category totals in the summary; category-code filters on record pages; IPC. Verified by behavior tests, including the sync failure reproduced first, and by measuring coverage on real data.
3. Merge and detail data: strong match and reasons, the batch confirm command, merge time, 合併紀錄 from decision events, the global pending count and affected amount, card mask (`****dddd`) and billing period on records, the month's largest purchase, same-merchant count and total, and search by merchant text or amount within a month.
4. UI: page A, modal B, modals C and D per DESIGN.md; projection and twelve-month statistics in the insights module; delete the legacy renderer category classifier in `src/lib/spending/categories.ts`. Verified in the real app at 1280 and 980 with values hidden and the blur leak probe.
